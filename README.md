# Harukoto Project Server Manager

複数のUbuntuサーバーを、1つのデスクトップアプリからまとめて管理・監視するためのクライアントアプリです。Windows / macOSの両方で利用できます。

CPUやメモリ、ディスクの使用状況を見たり、サーバー上のプログラムを起動・停止したり、ブラウザ感覚でサーバーにログインして操作したりといった作業を、コマンドを直接打つことなく行えるようにすることを目的としています。

> **注意**: このアプリは単体では動作しません。管理したいUbuntuサーバー側に、対になる常駐プログラム「`server-manager-api`」を事前にセットアップしておく必要があります。サーバー側のセットアップ方法は`server-manager-api`のドキュメントを参照してください。

## インストール方法

最新版は GitHub の [Releases ページ](../../releases) から入手できます。ページ内の「Assets」から、お使いのOSに合ったファイルをダウンロードしてください。

### Windows

1. `Server-Manager-Setup-x.x.x.exe` をダウンロードします。
2. ダウンロードしたファイルを実行し、画面の指示に従ってインストールします。
3. インストール後、スタートメニューまたはデスクトップのショートカットから起動できます。

### macOS

1. お使いのMacに合わせて、`.dmg`ファイルをダウンロードします(Apple Silicon(M1以降)は`arm64`、Intel Macは`x64`)。
2. ダウンロードした`.dmg`を開き、アプリケーションフォルダにドラッグしてインストールします。
3. 初回起動時に「開発元が未確認のため開けません」といった警告が表示される場合があります。これは、このアプリがApple公式の署名(有料の開発者登録)を行っていない未署名ビルドのためで、悪意のあるソフトということではありません。以下の方法で起動してください。
   - Finderでアプリのアイコンを **右クリック(またはControlキーを押しながらクリック)** し、メニューから「**開く**」を選択する
   - 表示される確認ダイアログでもう一度「開く」を選択する
   - 一度この方法で起動すれば、以降は通常のダブルクリックで起動できます

## はじめに(サーバーの追加)

アプリを起動すると、まず「ノード」(管理対象のサーバー)を登録する必要があります。

1. サイドメニューの「ノードを追加」などのボタンから追加画面を開きます。
2. 以下の情報を入力します。管理したいサーバーの管理者(または自分でサーバーをセットアップした場合はその際の設定)から入手してください。
   - **ホスト名 / IPアドレス**: サーバーのアドレス
   - **ポート番号**: `server-manager-api`が動作しているポート
   - **アクセストークン**: サーバーへの接続を許可するための合言葉のようなものです。サーバー側で`server-manager-api`を初めて起動した際に自動生成され、ログやファイルに出力されています
3. 入力後、接続テストが行われます。成功するとノード一覧に追加され、以降はサイドメニューからそのサーバーを選んで各機能を利用できます。
4. 複数のサーバーを登録した場合は、いつでも一覧から切り替えて操作できます。

入力したアクセストークンは、OS標準の安全な保管機能(Windowsの資格情報保護など)で暗号化して保存されるため、平文でパソコンに残ることはありません。ノードを削除すれば、保存されていたトークンも合わせて破棄されます。

## 使い方ガイド

サイドメニューから、以下の各機能にアクセスできます。専門的な言葉はできるだけ避けて説明しています。

### 概要(ダッシュボード)

選択中のサーバーのCPU使用率・メモリ使用量・ディスク使用量・ネットワーク通信量などを、グラフや数値でひと目で確認できるトップページです。サーバーが「今どのくらい忙しいか」を素早く把握したいときに使います。

### ストレージ管理

ディスクの空き容量や使用量の推移をグラフで確認できます。過去のデータはアプリ側に自動的に記録されていくため、「先週と比べてどれくらい容量が増えたか」といった変化も追いやすくなっています。

### systemdサービス

サーバー上で動いている各種サービス(バックグラウンドで常に動作しているプログラム)の一覧を確認し、起動・停止・再起動などの操作を行えます。

### ネットワーク

サーバーが持つネットワークの接続口(インターフェース)の情報を確認できます。

### Docker

サーバー上で動いているDockerコンテナ・イメージ・ボリューム・ネットワークの一覧を確認し、起動・停止などの操作を行えます。Dockerを使っていないサーバーの場合は特に使う必要はありません。

### ゲームサーバー管理

Minecraftなどのゲームサーバーを一覧・管理できる機能です。

### プロセス管理

Node.jsやPythonなどで作られた自分のプログラム(プロジェクト)をサーバーに登録し、開始・停止やログの確認をブラウザ感覚で行える機能です。

### Webターミナル

ブラウザのような画面の中で、サーバーのLinuxシェル(コマンドライン)を直接操作できる機能です。使い慣れた黒い画面の操作を、SSHクライアントなどの別ソフトを用意せずにこのアプリの中だけで行えます。

- サーバーに登録している **Linuxユーザー名とパスワード**でログインします(ノード追加時のアクセストークンとは別物です)。
- 複数のサーバー・複数のセッションを、ブラウザのタブのように切り替えながら同時に開いておくことができます。
- 入力したパスワードは、ログイン処理にのみ使われ、アプリ内に保存されることはありません。

### ツール:Cursor使用量の推定

AIコーディングツール「Cursor」の利用履歴CSVファイルをアップロードすると、使用トークン数やおおよその費用をグラフで確認できるツールです。

### システム設定

サーバー本体の各種設定(ホスト名、日付・時刻、ユーザー管理、SSH鍵、ファイアウォール、自動更新の有効化など、19項目)を、画面上から確認・変更できます。サーバーの基本的な構成を変更したいときに使います。

## アプリの自動更新について

このアプリには自動更新機能があり、新しいバージョンが公開されると起動時に自動的にチェックし、必要に応じてダウンロード・更新が行われます。基本的に手動での再インストールは不要です。

また、サーバー側の常駐プログラム(`server-manager-api`)についても、システム設定の画面からアプリ経由で更新を実行できます(最新のコードの取得・必要なファイルの更新・再起動までを自動で行います)。

## よくあるトラブル

**サーバーに接続できない / 「接続に失敗しました」と表示される**

- サーバー側で`server-manager-api`が起動しているか確認してください。
- 入力したホスト名・IPアドレス・ポート番号に誤りがないか確認してください。
- 入力したアクセストークンが正しいか確認してください(サーバー再起動などでトークンが変わっている場合があります)。
- サーバーとパソコンが同じネットワーク上にあるか、またサーバー側のファイアウォールでポートが許可されているか確認してください。

**Webターミナルにログインできない**

- 入力しているのは「ノード追加時のアクセストークン」ではなく、サーバーに登録された**Linuxユーザー名とパスワード**です。両者を混同していないか確認してください。
- サーバー側でSSHログインの設定(sshd)が有効になっているか確認してください。

**macOSで「開発元を確認できないため開けません」と表示されて起動できない**

- [macOSへのインストール手順](#macos)にある、右クリック(Controlキー+クリック)から「開く」を選ぶ方法をお試しください。

**上記で解決しない場合**

- サーバー管理者、またはこのアプリの開発者にお問い合わせください。

## 開発者向け情報

以降はエンジニア向けの技術情報です。利用するだけであれば読む必要はありません。

### 技術スタック

- Electron + electron-vite + React + TypeScript
- UI: 自前実装の shadcn/ui スタイルコンポーネント(`src/renderer/src/components/ui`) + Tailwind CSS
- モーション: Framer Motion(Apple Designの動作原則に準拠)
- ルーティング: React Router / データ取得: TanStack Query / 状態管理: Zustand
- ローカル設定: `conf` + `js-yaml` による `config.yml`

### セットアップ

```bash
npm install
npm run dev
```

### ローカル設定・キャッシュの保存先

すべてのローカル設定・プリファレンス・キャッシュは以下に集約される(`src/main/paths.ts`)。

```
%APPDATA%\Harukoto Project\Server Manager\
├─ config.yml        # プリファレンス・登録ノード一覧 (YAML)
├─ secure\           # ノードごとのセッショントークン (Electron safeStorageで暗号化)
├─ Logs\
└─ Crash Dumps\
```

セッショントークン等の機微情報は `config.yml` には含めず、Electronの `safeStorage`(Windows DPAPI等)で暗号化して別ファイルに保存する。

### ページ/モジュールのテンプレート機構

`src/renderer/src/modules/<feature>/index.tsx` が1つの機能ページ(`ModuleDefinition`)に対応し、`src/renderer/src/modules/registry.tsx` に1エントリ追加するだけで、サイドメニュー・ルーティングの両方に反映される。シェル本体(`AppShell`/`Sidebar`)を変更する必要はない。

```
src/renderer/src/modules/
├─ types.ts        # ModuleDefinition型
├─ registry.tsx     # モジュール一覧(新規追加時はここに1行足すだけ)
├─ overview/        # 概要(モニタリング)
├─ docker/          # Dockerコンテナ/イメージ/ボリューム/ネットワーク
├─ systemd/         # systemdサービス
├─ system-settings/ # apt・UFW・ユーザー等
├─ game-servers/    # Minecraft/ゲームサーバー(Pterodactyl連携)
├─ process-manager/ # Node.js/Pythonプロジェクト管理
└─ terminal/        # Webターミナル(Linuxユーザーログイン + xterm.js)
```

### ノードへの接続(V1: アクセストークン方式)

パスキー(WebAuthn)による認証はElectronの`file://`起源では正規のRP IDを持てないため、まずは共有アクセストークンによる暫定接続方式で実装している(`src/renderer/src/lib/node-api-client.ts`)。

1. `server-manager-api`側を起動すると、初回のみアクセストークンが自動生成されログと `data/access-token.txt` に出力される(`.env`の`API_ACCESS_TOKEN`で固定値を指定することも可能)。
2. クライアントの「ノードを追加」ダイアログで、ホスト・ポートに加えてこのアクセストークンを入力する。
3. 送信すると `GET /health` で疎通確認 → 認証必須エンドポイントでトークン検証を行い、両方成功した場合のみノードを登録する。
4. トークンはElectronの`safeStorage`(Windows DPAPI)で暗号化され、`config.yml`とは別ファイルに保存される。ノード削除時は自動的に破棄される。
5. ノード一覧の接続バッジ、概要ページのCPU/メモリ/ディスク/ネットワークは、このトークンを使って`server-manager-api`から取得した実データを表示する(`use-node-health.ts` `use-node-access-token.ts`)。

WebSocket(コンソールログ等)は、ブラウザ標準のWebSocket APIが独自ヘッダーを送れないため `?token=` クエリパラメータで同じアクセストークンを渡す仕様になっている(API側 `src/server.ts` 参照)。

パスキー(WebAuthn)は`server-manager-api`側にAPIとして骨格は残っているが、上記の暫定方式からは呼び出しておらず、将来のノード個別登録機能として置き換え予定。

### Webターミナル(ノード上のLinuxユーザーでログイン)

`terminal`モジュールは、共有アクセストークンによるノード接続(上記)とは別の、もう1段階のログイン画面を持つ。

1. サイドメニューの「ターミナル」を開くと、まずユーザー名/パスワードの入力フォームが表示される。
2. ログインすると、クライアントはWebSocket(`/terminal/session`)経由でノード自身のsshdへユーザー名/パスワードを送り、`server-manager-api`が`ssh2`クライアントとして`127.0.0.1`のsshdに接続する(認証・権限はLinux/PAM側にそのまま委ねる)。
3. 認証に成功するとPTY(シェル)の入出力がWebSocketで中継され、`@xterm/xterm` + `@xterm/addon-fit`でブラウザ内に表示される。
4. パスワードはメモリ上でWebSocket送信に使うのみで、`config.yml`・`safeStorage`・ログ・監査ログのいずれにも保存されない。ログイン/切断イベントのみ`server-manager-api`側の監査ログに記録される。

サーバー側で接続先ホスト/ポートを変更したい場合は`server-manager-api`の`.env`の`TERMINAL_SSH_HOST` / `TERMINAL_SSH_PORT`を設定する(デフォルトはノード自身の`127.0.0.1:22`)。

### macOS対応ビルド

`v*.*.*` タグをpushすると、GitHub Actions(`.github/workflows/release.yml`)がWindows/macOSの両OSでmatrixビルドを行い、GitHub Releasesにそれぞれの成果物を公開する。

- macOS向けターゲットは `dmg`(配布用)と `zip`(`electron-updater`のSquirrel.Macによる自動更新に必須)を `x64` / `arm64` それぞれで生成する。
- Apple Developer証明書が未設定のため、現状は**未署名(unsigned)ビルド**である(`electron-builder.yml`の`mac.identity: null`、CIの`CSC_IDENTITY_AUTO_DISCOVERY: false`)。ユーザーが起動する際はGatekeeperの警告が出るため、右クリック(または Control+クリック)→「開く」での起動が必要になる。
- macOS用アプリアイコン(`build/icon.icns`)は未用意。現状Windows用の`.ico`も存在しないため、`electron-builder`のデフォルトElectronアイコンが使われる。独自アイコンを設定する場合は、1024x1024程度の元画像から`iconutil`(macOS)や`png2icons`等のツールで`build/icon.icns`(Windows向けは`build/icon.ico`)を生成し配置する。
- 将来的に署名・公証(notarization)を行う場合は、以下の対応が追加で必要になる。
  - Apple Developer Program登録・配布用証明書(Developer ID Application)の取得
  - `electron-builder.yml`の`mac.identity`をnullから証明書名に変更(または削除)し、`mac.hardenedRuntime: true`・`mac.entitlements`等の設定を追加
  - CIに`CSC_LINK`(証明書.p12のbase64)・`CSC_KEY_PASSWORD`・`APPLE_ID`・`APPLE_APP_SPECIFIC_PASSWORD`・`APPLE_TEAM_ID`をsecretsとして追加し、公証には`@electron/notarize`(electron-builderが自動連携)を利用する

- system-settingsはまだプレースホルダー表示のみで、`server-manager-api`側のエンドポイントとの実接続は未実装(TODO)。
